# ABS 2.37.1 bump — design

**Date:** 2026-10-01
**Status:** implemented

## Problem

ABS v2.37.0 (2026-09-28) and v2.37.1 (2026-09-29) are out; abs-cli's tested
ceiling is 2.36.1.

One 2.37.0 change breaks a documented CLI path. `PATCH /api/items/:id/cover`
(`items cover set --server-path`) now requires the path to be one of the
item's scanned library files — `CoverManager.validateCoverPath` checks
`libraryItem.libraryFiles[].metadata.path` and otherwise returns
`500 Invalid cover path` (`LibraryItemController.updateCover`). Previously any
existing image file on the server was accepted.

Observed against 2.37.1 with the current suite: the smoke run aborts in the
Cover section at the `--server-path` step. Its fixture re-links the cover that
`--file` stored under `/metadata/items/<id>/cover.png`, which was never a
library file. By hand: `500 Internal Server Error — Invalid cover path`,
exit 2.

## Other 2.37.x changes (v2.36.1...v2.37.1, `server/`)

None affect abs-cli:

- Cover / author image cache endpoints require a UUID id and positive integer
  width/height — abs-cli never sends width/height.
- `GET /api/libraries/:id/series/:seriesId` 404s for a series from another
  library — correct 404 handling.
- Invalid filter values no longer crash the server (`libraryFilters.decode`).
- Collapse-subseries sort validated against an allow-list.
- Audible match results gain `explicit` — additive, passes through.
- API keys accepted on websockets; OIDC cookie/session fixes (2.37.1) — not
  used by abs-cli.

## Decision

Thin pass-through: the CLI does not pre-validate the path (that would mean
fetching the item and mirroring server policy). The restriction is surfaced in
help text and pinned by smoke.

Smoke asserts the rejection unconditionally. Per the support policy, smoke on
the floor decides the floor: if 2.36.x fails only that assertion,
`MinSupportedVersion` rises to 2.37.0 (same method as the 2.33.1 → 2.34.0
raise).

## Design

### CLI — `items cover set` (help only, `src/AbsCli/Commands/ItemsCommand.cs`)

- `--server-path` description: `Path of an image already among the item's library files`.
- Help Notes (caveats): ABS rejects any other path with 500 "Invalid cover
  path" — e.g. a cover stored under `/metadata` by `--file`; and an accepted
  image is copied to `/metadata/items/<id>/` (unless `storeCoverWithItem`),
  so the response `cover` is the copy, not the given path
  (`validateCoverPath` copies anything outside the item's cover dir).
- Example path: an item-folder path, `/audiobooks/Author/Title/cover.jpg`.
- No version qualifier — with the floor at 2.37.0 every supported server
  enforces it.

### Smoke — Cover section (`docker/smoke-test.sh`; `seed.sh` untouched)

Replace the `--server-path` block:

1. Read FIRST_ITEM's `relPath` (`items get`) and split it into
   author/series/title segments (seeded items have no sequence).
2. As `uploaduser`, `abs-cli upload` the fixture PNG with those values and the
   library's folder — ABS `ensureDir`s the existing item folder and adds the
   file. Assert the receipt `relPath` equals the item's.
3. As root, `items scan --id FIRST_ITEM_ID`; find the PNG in
   `items get --expanded` `libraryFiles[].metadata.path`.
4. `items cover remove` (the scan may have auto-assigned the new image), then:
   - **Positive:** `cover set --server-path <library-file path>` succeeds with
     `cover == /metadata/items/<id>/cover.png` (the copy; assumes the default
     `storeCoverWithItem=false`), and `coverPath` equals that returned cover.
     Then `items cover remove`.
   - **Negative** (no cover set): `cover set --server-path
     /metadata/items/<id>/cover.png` exits non-zero with `Invalid cover path`
     on stderr.
5. The PNG stays in the folder; later sections are unaffected (verified:
   344/344 on 2.37.0 and 2.37.1).

### Version range

- `MaxTestedVersion` 2.37.1; docker-compose and CI smoke image 2.37.1; README
  range; CLAUDE.md and `docs/abs-compatibility.md` clone tag; `abs-api-coverage.md`
  tested range; ceiling unit test.
- Run smoke on 2.36.1. If only the negative assertion fails: `MinSupportedVersion`
  2.37.0 with an updated rationale comment; smoke on 2.37.0 must pass.
- `docs/abs-compatibility.md`: `1.1.4+` row becomes `1.1.4` (2.34.0 — 2.36.1);
  new `1.1.5+` row (2.37.0 — 2.37.1) with the floor evidence and 2.37 notes;
  the "older than supported" example message names the new floor.
- `LibraryItemExpanded.NumFiles` comment: drop the stale "older supported
  servers (2.34.0 — 2.35.1)" wording.

No README Commands-table change (no verbs or flags added/removed).

## Testing

- Unit: full suite; ceiling test expects 2.37.1.
- Smoke on fresh stacks: 2.37.1 344/344, 2.37.0 344/344, 2.36.1 343/344
  (only the negative assertion fails — the floor evidence; floor raised to
  2.37.0).
- CI on the PR.
